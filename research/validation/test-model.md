# 验证模型与证据可信度

研究时间：2026-07-27 至 2026-09-23。记录仓库自检收敛、E2E 所有权和验证盲区的设计依据。当前命令与覆盖范围见 [E2E README](../../e2e/README.md)及[验证说明](../../doc/reference/verification.md)。

## 为什么收敛仓库自检

2026-07-27 的原审计记录了 42 份 source-policy 测试、51 份 package-contract 测试、47 份 coverage-contract 文件，以及 284 个 tools 文件。大量检查读取源码、目录清单或由同一源码生成的清单，再断言它们符合预设形状。这些数量只描述历史问题规模。

采用的边界是：编译器验证类型，格式与 lint 工具验证写法，单元测试验证确定性行为，E2E 验证真实进程、协议、服务和发布产物。包清单与 source inventory 的自洽，不能证明安装后的调用行为。删去重复自证体系，不等于删去信任边界验证、真实清理或负向用例。

## 断言与资源的归属

- 业务不变量由 package/example 测试拥有；根 runner 负责选择、调度、deadline、结果汇总和资源清理。
- example 由真实输入集合动态发现，实际参与者、结果与完成命令必须对应，缺失、重复或意外参与者均不能被计作成功。
- 进程清理由创建者拥有，并需要进程身份、排空与退出证据。runner 不是恶意进程沙箱，不从普通 E2E 推导宿主机 containment 能力。
- Docker 记录本次 owner 创建的精确 ID、tag 和标签；清理后独立读回。不能使用全局 prune 或按相似名称猜测归属。
- E2E 的职责是证明组合行为；不把声明了一个 suite 或生成了 summary 当成执行过该场景。

## 发布包与运行时

真实 tarball 必须只通过安装后的 package name 解析，不能回落到 workspace 源码。export target 缺失的物理产物应失败，合法产物应能导入；这与读取源码 manifest 检查固定字段不同。

原生 HTTP/2、Fetch、mTLS 与 streams 要按实际 runtime 分别取证。观察到的工具版本是实验条件；一般执行资格与依赖/fixture 固定的区别见[工具链策略](toolchain-policy.md)。

## 防止测试替被测对象完成工作

2026-09-23 的研究计划提出了几个验证问题，原始报告位于临时目录，未随仓库保存；它们在这里仅作为实验设计依据，不视为本次已复现或已修复的缺陷：

- 检测遗留子进程时，测试运行器若自动清理 orphan，会隐藏被测 runner 的清理缺陷；断言应先观察残留，最后再做测试自身 cleanup。
- 生成胶水需要验证 service options 透传，例如 `readMaxBytes` / `writeMaxBytes`，且超限请求应在 handler 前拒绝。
- “同一进程重建对象”与“新 PID 恢复”是不同实验；两者都不能自动证明高可用、备份或容量。
- 上游运行时缺陷需要保留版本与最小复现，不通过库层绕过测试来制造通过结果。

## 有限实验与长期证据

10 秒 soak 只能证明短时 workload、结果标记和清理路径；持续至少 60 分钟的结论需要实际完成对应时长的运行。RPS、延迟、RSS、heap 和资源数量必须连同硬件、版本、负载与时间窗报告，不设置脱离环境的通用性能承诺。

原 E2E 记录在提交 `3fb895bd41daebd48cf37765aeb51892fabdaca2`、tree `7185fe57e1854c9e34de516397dbfd9fa842e0db` 上报告：macOS 26.5.2 arm64、Bun 1.3.14、Node 26.5.0、TypeScript 7.0.2、Docker 29.6.2；有限 E2E 为 53/53，examples 为 44/44，残留为 zero-observed。该历史结果不包含 60 分钟 soak，也不替代当前完整矩阵。

## 后续演变

早期方案把 Proto 和所有 Docker CI 路径排除在外；之后已加入 Buf/Protobuf，且当前 coverage 中包含部分真实 Docker 场景。研究保留的是“各类证据不能互相冒充”的理由，具体脚本、数量和运行范围由当前仓库与实际执行结果决定。
