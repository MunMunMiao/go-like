# 架构探索：core 合并方案与从零发散设计（2026-11）

研究时间：2026-11-16。仓库基线：`main` 64492e7。本文是探索性研究记录，设计稿中的 API 不代表当前公共接口；实验结论受文中运行时版本约束。

## 研究问题

1. **线 A：** 首次发布前，把 19 个没有第三方运行时依赖的包合并为一个 `@go-like/core`（原包变为 subpath，其余 26 个包独立发布并 peer 依赖 core），这一方案有哪些必须修正或值得优化的地方？
2. **线 B：** 以 go-micro、go-kratos、go-zero 为参照，如果从零为 TypeScript 设计 Go 风格微服务工具包，包、模块与核心概念应如何组织与解耦？这些设计反过来能为现有架构提供什么？

## 线 A 结论

合并方案没有发现硬伤。必须做的是保证运行时只有一份 core 实例，并把代码生成器与发布流水线一起迁移；其余多数候选只带来源码归属与公开面上的整理收益。

### 必须做

1. **保证全应用只有一份 core 实例。** 模块级身份状态在副本之间不互通：双副本实验中 metadata 跨副本读取为 `null`，broker subscription 终态丢失，struct 以私有 `Symbol` 判定而互不承认；两份副本交替构造的 20,000 层 Context value 链在 Node 26 上栈溢出，同一副本正常。包管理器原型显示，适配器以 `dependencies` 声明 core 时，npm、bun、pnpm 均安装两份并导致身份判断失败；改为 peer 后版本不匹配时，npm 报 ERESOLVE，pnpm 警告，bun 静默只装一份。做法：适配器 peer 依赖 core 并 lockstep 发布；保持现有单次多入口构建；在发布验证与运行时加入“唯一实例”断言，作为 bun 静默场景的兜底。
2. **代码生成器随迁移同步修改。** `protoc-gen-like` 生成的代码写入旧包名，合并后会生成不可用的 import。
3. **lockstep 覆盖生成器自报版本、精确内部依赖与发布验证中的版本断言。**

构建原型确认：现有 `tsdown.config.ts` 原样接受嵌套 subpath 入口，共享模块进入同一 chunk，`ServiceErrorBrand`、`MetadataBrand`、`localContextNodes`、`TransportInfoBrand` 各只有一份定义；Node 与 Bun 的跨入口身份断言通过。同一包内不会因多入口而分裂实例。

### 应该做

- 明确划界标准后，重新判定 transport-http 是并入 core 还是保持独立 provider。它没有第三方运行时依赖，Fetch 根入口与 Node 子路径已经分离；无论哪种都不应让它悄悄成为默认实现。
- config 的归属作为产品决策处理：`js-yaml` 只在 `./yaml` 子路径中使用，根入口没有 Node API。
- `protoc-gen-like` 是构建期工具，不应 peer 依赖 core。
- 可选：以 `./<module>/testing` 发布 conformance 套件，供第三方 provider 复用；这会成为新的公开承诺。

### 值得做

- 合并后基础模块之间改用相对导入，provider 子路径只保留适配器真正需要的 SPI。目前 `transport/provider` 混有 client 与 server 内部的线上编解码。
- `waitForContext`、`Server`、`Endpointer` 只依赖 Context：保留 `./lifecycle` 作为低层稳定入口，整理契约类型的声明归属，并用 lint 约束低层模块不得导入 app。外围包对 `Server` 的引用均为 `import type`，因此这项只改善归属清晰度，不减少运行时依赖。
- 测试与覆盖率流水线需要逐项重接：`bunfig.toml` 的测试根与按目录忽略规则、按 workspace 统计的覆盖率校验、测试相对路径、tsconfig references、发布 consumer fixture 中的旧包名。
- 发布验收改为按公开子路径的最小 consumer，并同时验证 JS 与 DTS 依赖图的可移植性。
- 在[包拓扑设计](../../designs/package-topology.md)中说明演变：该文否决的是聚合默认实现的总管门面，本方案不做根入口 barrel、不聚合默认实现。

### 已驳回

- “app 不应依赖 registry”：这是正常的向下依赖，快照校验保证注册与注销的实例身份一致。
- “把身份品牌改为 `Symbol.for` 等跨副本安全形式，从而放松 peer 与 lockstep”：本地节点表同时承担把递归改写为循环的职责；`Symbol.for` 还带来跨 realm、键名碰撞、抢先占位与版本间值形状冲突等问题。身份正确性要求“唯一规范实例”或“完整互操作协议”二选一；全仓 lockstep 不是数学必要条件，但在没有互操作协议之前，它是保证唯一实例最便宜的手段。

### 跨设计规律

1. **期限必须作为显式数据存在。** 试图只用 `AbortSignal` 承载取消与期限的 M2 被判致命；Wire 用请求头跨进程传递剩余预算，进程内仍需 `WeakMap` 侧状态取回原始截止时间。Go `Context` 把 deadline、取消与值绑在一起是承重设计，替换它的方案最终都要重建同样的信息。这支持仓库继续自持 Context 实现。
2. **私有身份登记可以避免，但代价会转移。** Wire 原设计以 `WeakMap` 侧状态保存请求期限，原型证实它在两份模块副本之间断开，与线 A 讨论的跨副本问题同构。把需要跨组件存活的状态编码进线上数据（例如绝对期限请求头）后，原型在副本之间也能正确传递期限，不再依赖唯一实例；代价转为跨机时钟一致或线上格式的兼容承诺。因此“唯一规范实例”与“完整互操作协议”的二选一对所有设计都成立，后者可以通过把状态外置到线上数据来实现。
3. **拓扑作为数据出现了两次。** 两名未读仓库的设计者独立地把“依赖连向何处”从代码移到拓扑输入：Loom 在构建期链接，Topo 在启动时绑定。这是 go-zero 由 goctl 拥有整条链路的激进延伸。 Loom 原型否定了把拓扑做成构建期链接输入的收益：受限声明只覆盖 71.1% 的需求，生成胶水加声明的代码量是手写装配根的 2.07 至 2.93 倍。拓扑更适合作为描述与校验产物，而不是装配机制。
4. **服务发现被降级。** 三份盲设计都没有把 Registry 放进最小概念集：Wire 把它藏进一个 wrap 的内部端口，Loom 视其为链接目标的实现，Topo 把它降为清单中的一个字段。go-micro 与 kratos 则都将其作为一等接口。
5. **共享内核先于路线选择。** 审查者指出，停止次序、快照式服务目录、调用预算语义与保守默认值是各路线共有的部分，应无论选哪条路线都先做成共享内核。这与线 A 的结论方向一致：真正稳定的是生命周期契约与期限语义。
6. **治理默认值分三派。** 默认关闭、预设开启、宿主强制开启。go-zero 默认全开导致“多层拒绝来源难以排查”，Wire 提出以拒绝来源响应头与诊断事件回应。

## 对现有架构的启示

- 保持自持 Context，并把“期限是显式数据”写进设计说明，作为不迁移到 signal-only 模型的理由。
- 把线 A 的“唯一实例”断言视为所有路线共同需要的基础设施，而不只是合并方案的补丁。
- 可借鉴 Wire 的治理拒绝可观测性：拒绝来源响应头与诊断事件。
- 可借鉴 Loom 与 Topo 的拓扑描述：作为文档、调试或 CI 产物输出服务依赖图。Loom 原型表明不宜把它做成生成装配代码的链接器。
- Loom 原型保留下来的 Loom-lite（proto、Connect、手写装配根、共享生命周期内核）与 go-like 现有做法一致，可作为维持显式组装路线的外部佐证。
- 可对照 Wire 作者的 Node 排空观察：排空期间响应加 `connection: close`，否则关闭要等待空闲 keep-alive 超时（作者实测 3.3 s 对 0.35 s）。需与现有 Node host 的排空行为核对。

## 原型

两个排序第一的设计各有一条“一旦不成立即否决设计”的假设，分别做了原型验证。原型位于仓库之外，不进入发布物。

### Wire：调用语义不依赖私有请求登记

结论：在补两条线上约定后成立。

| 场景                                                      | Node v26.13.1                                               | Bun 1.4.4                             |
| --------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------- |
| 200 ms 预算等待 60 ms 后，经 URL 重建传到下游的剩余预算   | 136 ms                                                      | 138 ms                                |
| 失败后重试                                                | 两次换节点，预算从 200 ms 降到 175 ms；非幂等请求只发送一次 | 预算降到 178 ms；非幂等请求只发送一次 |
| 取消送达下游                                              | 1.8 ms                                                      | 0.8 ms                                |
| 以错误结束的流                                            | 3 条消息后返回 `unavailable`，该节点失败计数加 1            | 同                                    |
| 入站与出站使用两份模块副本，按原设计以 `WeakMap` 保存期限 | 剩余预算被重置为 200 ms，已消耗的 60 ms 丢失                | 同                                    |
| 入站与出站使用两份模块副本，改用绝对期限请求头            | 137 ms                                                      | 139 ms                                |

需要补的两条约定：

1. 期限写进线上数据而不是进程内状态：入站把绝对截止时间写入请求头，后续每跳原样复制。代价是依赖跨机时钟一致，时钟偏差未测；gRPC 线上使用相对超时正是为了避开这一点。
2. 流终止结果回传：mesh 在响应上标注节点，客户端把流结束结果回灌节点选择；通用 Wrap 看不到 body 内的结束错误。

对照 go-like 现状：客户端在每次尝试时依据调用方截止时间重新计算相对超时并写入 `Go-Like-Timeout-Ms`（`packages/client/src/index.ts:472`、`:486`），服务端读取后派生期限（`packages/server/src/index.ts:666-668`）；进程内的期限由自持 Context 携带。这与 gRPC 一致，不受时钟偏差影响，在满足线 A“唯一实例”前提时也没有 Wire 的 `WeakMap` 断裂问题。

未覆盖：熔断、限流与追踪；非幂等请求在字节尚未发出时的重试；服务端以期限取消 handler；长流不受期限约束。

### Loom：受限声明覆盖部署拓扑

结论：否定。覆盖率未达到 80%，链接器相对 Connect-ES 加手写装配根也不省代码。

原型按审查意见把 manifest 拆为契约、依赖槽位、构建拓扑与每实例运行期参数，为 3 种服务形态（带鉴权的公开 HTTP 网关、使用服务发现与 KV 并含 server stream 的内部 RPC、消费事件的 worker）与两套环境（单进程、多进程多副本）编写声明，并实现一个 396 行的生成器。

| 需求范围     | 可声明 / 总数 | 覆盖率 |
| ------------ | ------------- | ------ |
| 全部         | 32 / 45       | 71.1%  |
| 三种核心形态 | 28 / 28       | 100%   |
| 接入层       | 10 / 15       | 66.7%  |
| 运行期参数   | 9 / 12        | 75%    |

无法用受限声明表达、必须开逃生口的 13 类需求：webhook 原始 body 与 HMAC 校验；自定义状态码、响应头与 cookie；SSE；挂入现有 Web 框架；JWT 或 OIDC 鉴权；条件依赖；自定义负载均衡与亲和性；按业务错误重试；密钥轮换；热更新；自定义中间件顺序；consumer 并发与分区；死信策略。

代码量对比（排除 32 行业务代码与 371 行共享运行时）：

| 环境         | Loom 生成胶水加声明 | 手写基线 | 倍数 |
| ------------ | ------------------- | -------- | ---- |
| 单进程       | 104 + 133 = 237     | 81       | 2.93 |
| 多进程多副本 | 213 + 182 = 395     | 191      | 2.07 |

只比较生成胶水，Loom 仍多于手写（104 对 81，213 对 191），且生成器本身的 396 行未摊薄。

功能层面全部可行：生成产物与手写基线在两套环境、两个运行时上共 8 个组合全部实测通过，覆盖 HTTP GET 到内部 RPC、NDJSON server stream、401、安全的 500、worker 事件、双副本轮询、杀掉一个副本后继续服务与注册中心注销。另外实测通过：生成结果逐字节确定；端口占用时启动回滚；SIGTERM 时排空在途 stream；以实际绑定端口登记地址。调试方面，生成产物比手写多一层包装栈帧；手写基线曾漏写按调用创建的闭包，生成器在结构上避免了这类错误，但修复只涉及两处、数行。

保留方向：撤回链接器，保留 proto、Connect、手写装配根与共享生命周期内核，即 Loom-lite。go-like 现有的 Buf/Connect 传输与“组合而非容器”的装配方式与之一致。

未覆盖：生成 TypeScript 类型与严格模式类型检查；HTTP/2 gRPC 与 grpc-go 的互通；真实 etcd 或 Consul；200 个 operation 的规模；重试故障注入；性能与背压。原型所需的 `@connectrpc/connect-node` 2.3.0 未在仓库中安装，仅解压到仓库之外的临时目录使用。

## 未验证与限制

- 线 A：完整合并产物的构建与全量测试；原型只合并了 context、metadata、struct、transport 四个模块。真实跨版本互操作、浏览器与 edge 运行时、Node 更早的 LTS 版本均未验证。
- 线 B：Loom 原型未覆盖类型生成、HTTP/2 gRPC 互通、真实注册中心与规模；Wire 原型未覆盖熔断、限流、追踪与跨机时钟偏差；Topo 的声明图确定性未验证；各设计中的代码样例大多只做了类型或语法检查，没有完整端到端运行。
- 参照事实：go-micro v4 到 v5 的完整破坏性变更清单、go-zero v1.x 期间是否存在语义不兼容，均未逐条核对。
