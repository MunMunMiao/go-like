## 判定规则

每个能力项都给出一个明确判定：

- **已对齐**：LikeGo 已具备同角色的公共契约和可执行实现；接口不要求逐字复制 Go。
- **部分对齐**：已有可执行核心，但同一能力仍缺少关键公共边界、provider 或完整调用链。
- **边界不同**：能力已经覆盖，但因 TypeScript、标准 Web API、原生对象所有权或产品决策而采用不同语义。
- **尚缺**：能力有价值，但实现、provider 覆盖或真实验证仍未闭环。
- **明确延期**：没有足够的产品协议或重复需求支撑公共抽象；当前能力可以由已有基础组件显式组合。
- **明确排除**：已经由用户批准不进入项目范围，不应伪装成待办或通过其他名称重新引入。

“已对齐”描述能力角色，不等于所有 provider 都已完成本地真实服务 E2E。存在 `src/` 或测试脚本也不等于
对应测试已经执行通过。

## 总体结论

LikeGo 已经不是单纯的生命周期适配器集合。当前代码已经形成 Context、App/Server、外部 Web、内部
Transport、Client/Server 服务调用、Registry/Discovery、五种 Selector、Resilience、Config、Store、
Cache、Broker/Event、Health、日志与 OpenTelemetry/Prometheus 的分层工具包。

与三个 Go 项目相比，LikeGo 当前明确的边界主要有四类：

1. 日志与指标包已为 Client、内部 Server、Web、Broker 提供显式请求包装，但仍坚持使用原生 Pino/Winston 和
   prom-client，不发布 Logger facade，也不安装全局自动 instrumentation。
2. Metadata 已有多值、规范化、16 KiB wire 上限和默认不传播的显式下游 allowlist/前缀投影；Server operation
   matcher 与 Client per-operation breaker 已进入公共 API。Discovery 默认采用权威空快照 fail-closed，并提供
   显式 `withBlock()`，只等待服务历史上第一次出现原始 endpoint；首次就绪后的空快照仍立即 fail closed。
3. 内部通信当前只支持 unary；项目没有连接级 full-duplex RPC stream。在 wire、half-close 与背压协议出现前，
   不用标准 Fetch body 冒充 RPC stream。
4. Transport、Store/Broker provider 与第三方 Server adapter 数量小于上游生态，但已有 HTTP/memory Transport、
   memory/NATS/RabbitMQ Broker、五种 Store 和五种 Registry provider。Registry 已冻结；其他 provider
   只由真实部署需求触发。

当前已经具备 Node HTTP 子路径的 Server 端 PEM TLS、mTLS 与 ALPN HTTP/2，以及原生 Client 的
CA/mTLS/SNI、ALPN HTTP/2 优先与 HTTP/1.1 回退，
`@likego/transport-memory` 的实例私有进程内 unary provider、`@likego/config/node` 的真实 Node 文件读取/监听，
以及 P2C+EWMA Selector、Kratos 式 Config Value、Cache memory/Redis、Kubernetes ConfigMap/Secret、
Vault Config/Store 与可恢复 RabbitMQ Broker。runtime 能力由显式
子路径承接，不把宿主连接池或全局 handler 伪装成 LikeGo 所有资源。

仓库包含可直接运行的 README-first 行业与框架示例。本地 E2E 覆盖真实进程、发布包 consumer 和需要 Docker
的 provider；具体执行范围以 `e2e/suites.ts` 与各 example 脚本为准。动态 Vault lease、
证书在线轮转、MQTT、SQL/ORM、Auth 与更多 provider 均因缺少当前业务协议而保持应用责任、条件项或非目标。

此外，LikeGo 所有公共包当前统一为 `0.0.1`，当前源码不能证明 npm 发布历史、生产采用、
升级兼容性或生态成熟度已经与三个 Go 项目对齐。

LikeGo 不应照搬 go-micro 的全局默认实例，也不应照搬 Kratos 的 Protobuf-first 路径。正确方向是保留
Go-style 的显式 Context、结构式小接口和清楚所有权，同时用标准 Web API 维持 Bun、Node.js、Deno 后端的
可移植性。

还要注意，当前 go-micro 已把自身定位从经典微服务框架扩展为 agent harness。它的 Agent、AI provider、持久化
Flow、MCP、A2A、x402、Model/Memory 和 agent 运维能力都是真实源码，但“上游已经实现”不等于“LikeGo 的微服务
基础范围必须补齐”。这些扩展在后文单独做范围判定，不能混入基础设施缺口。

### Unary 与双向流的边界

v1 的内部 Client、Server 和 Transport 只承诺 unary `Message`。外部 Web Handler 可以正常使用标准
`Request`、`Response` 和 Web Streams，但那属于应用选用的 Web 框架，不是内部 RPC Stream SPI。

真正的 full-duplex RPC stream 需要明确多次 `send/recv`、half-close、backpressure、取消和稳定 terminal error，
并选择 WebSocket、WebTransport 或其他真实 wire provider。在这些协议出现前，LikeGo 不发布 `newStreamClient`
或其他只包装一次 Fetch 的近似概念。

## LikeGo 当前验证边界

测试命令存在不等于已经执行通过。当前验证分为两类：

- `bun run test:unit` 运行不依赖外部服务的确定性单元测试；CI 还会执行格式检查、类型检查和构建。
- `bun run test:e2e` 在本地运行真实 provider、跨运行时、可执行 example 和发布 tarball consumer；需要 Docker
  的 suite 会启动真实服务并在结束后清理资源。长时间稳定性检查由 `bun run test:e2e:soak` 单独执行。

CI 不运行 E2E，也不上传机器自证产物。任何运行状态都应以当次命令的退出状态和日志为准，不能由 README、
历史报告、生成文件或脚本名称推断。

## 必须保持的设计边界

1. **gRPC/Protobuf 明确排除。** 这是用户批准的产品边界。标准 Fetch/Web Streams 只承接 half-duplex 的单次
   request/response body；未来 full-duplex stream 必须通过独立 WebSocket/WebTransport 协议和 provider 实现，
   不能重新引入 IDL、生成代码或 Protobuf runtime，也不能把 Fetch body 改名后冒充双向 channel。
2. **外部 Web 与内部 Transport 分离。** `@likego/web` 保持标准单参数 Fetch Handler；内部服务调用使用
   `@likego/transport`、`@likego/client` 和 `@likego/server`。Gateway 只能显式桥接，不能把两个域合并。
3. **Server 允许用户自由组合。** Core 只认结构式 `start(ctx)`、`stop(ctx)`；用户自建 Web 框架、
   Cron、consumer、control loop 或其他 Server 都应能直接接入。
4. **标准 Web API 是 portable 基线。** `Request`、`Response`、`Headers`、`AbortSignal`、Web Streams、Web
   Crypto 与注入的单参数 Fetch 优先；进程 signal bridge、Node socket、UDP、文件监听和第三方原生 SDK 必须隔离在
   runtime 子路径或 provider。
5. **保留原生数据面语义。** Broker ack/nack/DLQ、BullMQ job token、日志 transport、OTel provider 等仍由
   官方对象和应用拥有；LikeGo 只统一确实能够诚实表达的契约和生命周期。
6. **Go-style 不等于 Go 拼写。** Context 首参、functional options、小接口、显式 ownership 和 error value
   保留；TypeScript 导出函数继续使用 lower camel case。
7. **通用 Event Store、历史查询与框架级 replay 明确排除。** Broker 的 retention、offset、durable consumer
   与 redelivery 保持 provider 原生语义；业务审计和历史查询由应用数据层负责。未来如有独立产品需求，必须重新立项，
   不能以 go-micro、go-kratos 或 go-zlab 对齐为由重新引入。
