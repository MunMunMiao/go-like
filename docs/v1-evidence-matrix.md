## 中央来源证据清单

根目录 `e2e/cases/*.case.ts` 采用“一项规范化业务场景一个来源模块”。`e2e/contracts.ts` 把每个场景、服务和
清理结论绑定到机器可读字段；`e2e/suites.ts` 再独立核对 runtime、固定镜像、子进程树和 Docker 前后快照。

当前清单由 `bun run test:e2e:inventory` 动态生成：

- 81 个去重用例；
- 28 个 release-blocking suite；
- 15 个 Docker suite；
- 47 个官方来源；
- 16 个能力域，且没有 evidence-only suite。

Node 安全传输 gate 独立于上述 sourced inventory 执行，因为它验证的是同一 package 在两个 digest 固定 Node runtime
镜像中的发布实现，而不是新增第三方服务。它仍属于根 `bun run verify` 的强制阶段，任一 runtime、mTLS/ALPN 断言或
容器清理失败都会阻断终态。

历史迁移下限仍固定为 53 个业务用例和 6 个 Docker suite；新增能力只能抬高当前清单，不能篡改迁移基线来让
缺失验证通过。

## 明确边界

- v1 不支持 gRPC、Protobuf、IDL 或生成代码。
- v1 内部 Client/Server 只提供与 go-micro 对齐的 unary Transport 调用；既有 `Client` 自身管理按服务名懒加载的
  discovery watcher，并通过 `close(ctx)` 清理，不发布第二套 `ResidentClient`、`StreamClient` 或 Fetch Transport。
- 真正双向流、WebSocket 或 WebTransport 属于后续独立 Transport provider，必须先定义背压、半关闭、
  终态和真实 runtime/容器验证；v1 不把 Fetch `Request`/`Response` 或 unary `Message` 伪装成该能力。
- 外部 Web 与内部 Transport 分离；最小 scaffold 已实现，但 Gateway、Auth/JWT、更多 Transport provider、
  一致性哈希和 scaffold 之外的诊断 CLI 属于后续能力，不应在 v1 证据中伪装成已经完成。
