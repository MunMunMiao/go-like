# Referencia de paquetes y providers

Esta página está organizada según la pregunta que intenta resolver una aplicación, no según el layout del directorio `packages/`. Importa desde el paquete público más pequeño que sea dueño del contrato. El comportamiento específico del runtime se expone mediante un subpath explícito. Los paquetes provider no son implementaciones intercambiables con una única garantía universal.

## Cómo leer esta página

- **Contract** significa una interfaz portable o neutral respecto al provider.
- **Provider** significa una implementación respaldada por memoria, un archivo, un servicio de red o una biblioteca nativa.
- **Lifecycle adapter** significa un wrapper `Server` alrededor de un recurso nativo creado por la aplicación.
- **Evidence** identifica el tipo de respaldo del repositorio: source/export, pruebas declaradas o resultado de un comando local reportado. No convierte una versión de paquete en una afirmación sobre npm o producción.

El inventario de source actual contiene 43 manifests de paquetes `@go-like/*` no privados y 23 subpaths públicos de source, todos en la versión `0.0.1` en este checkout. Los 44 workspaces `examples/*` son aplicaciones privadas, no paquetes públicos.

## Matriz de decisión de runtime

| Entrada o familia de providers                                     | Source portable                               | Native de Bun/Node                                       | Afirmación sobre Deno                                  | Redacción de evidencia                                                                   |
| ------------------------------------------------------------------ | --------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| Context, Core root, Health, Metadata, Resilience, Struct           | Sí                                            | No requiere import nativo                                | Hay lanes de runtime seleccionadas declaradas          | Contrato de source; revisa la matriz ejecutada actual antes de redactar para una release |
| Web root y Web health                                              | Sí                                            | Requieren un host separado                               | Frontera Handler estándar                              | El Handler es portable; un Handler no es un listener                                     |
| Memory Transport, Memory Store, Memory Cache, Memory Broker        | Source local al proceso                       | Sin servicio externo                                     | Mismo significado local al proceso                     | No distribuido, durable ni entre procesos                                                |
| HTTP root y providers Fetch-backed de Config/Registry/Store        | Fetch inyectado                               | El runtime elige Fetch                                   | Respaldado por source donde exista la lane del paquete | Portable por source o lane declarada, no parity universal                                |
| Subpaths `/node`                                                   | No                                            | Específicos de Node, con posibilidad de ejecución en Bun | Sin entrypoint de Deno                                 | Un import explícito cambia el grafo de runtime                                           |
| NATS, RabbitMQ, BullMQ, Redis, Pino, Winston, SDKs nativos de OTel | Depende del provider                          | Fixtures Node/Bun o evidencia específica del paquete     | No infieras soporte de Deno                            | Lee el README del provider y el scope de E2E                                             |
| ZooKeeper                                                          | Sin soporte de Deno en el README del provider | Node/Bun                                                 | Explícitamente no soportado                            | No generalices desde el Registry root                                                    |

## Reglas para elegir funciones

- Usa `contextHandler` en el borde Web cuando necesites Context, no una bolsa custom de request del framework.
- Usa `newApp` y `server(...)` cuando un proceso tenga más de un recurso admitido o cuando quieras que la propiedad de signal y shutdown sea explícita.
- Usa `endpoint(...)` tipado y `handler(contract, fn)` cuando ambos lados deban compartir validación Struct en runtime. Usa `handler(service, endpoint, fn)` sin tipos cuando la aplicación sea dueña de otro contrato de bytes.
- Usa `withAddress(...)` antes de Discovery. Es más fácil de probar y hace explícita la identidad del destino.
- Usa `withDiscovery(...)`, `withSelector(...)`, `withFilter(...)` y `withBlock()` solo cuando el servicio necesite el comportamiento de plano de control que agregan.
- Usa `withRetry(...)` solo después de escribir la autorización de replay, el máximo total de intentos, el predicate de fallos y la idempotencia de negocio.
- Usa `newMemoryStore` para pruebas deterministas, no para afirmar durabilidad.
- Usa `newMemoryCache` para aceleración desechable, no como autoridad de citas o pagos.
- Usa `newBrokerServer` para conectar una suscripción a Core, no para obtener un worker de colas universal ni una API de settlement.
- Usa `newOtelServer`, `newPinoServer`, `newWinstonServer` o un Handler de Prometheus solo después de que la aplicación haya creado el provider o Registry nativo.

## Exclusiones explícitas

Ningún paquete del inventario público actual debe documentarse como dueño de gRPC, Protobuf, generación de código IDL, clients RPC generados, streams internos full-duplex, Event Store/historial/replay, autenticación/autorización genérica, comportamiento ORM, un service locator global u orquestación de clusters. Un provider o una aplicación puede usar una biblioteca ajena para una de esas responsabilidades, pero quedaría fuera del contrato actual de go-like.
