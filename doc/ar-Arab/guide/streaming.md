# التدفق

يعتمد go-like نموذج التدفق الموجود أصلاً في منصة Web. فالطلب المتدفق هو `Request` قياسي، والاستجابة المتدفقة هي `Response` قياسية قد يحمل جسمها `ReadableStream<Uint8Array>`. لا يضيف المشروع فئة تدفق خاصة، ولا DSL للإطارات، ولا قناة ثنائية الاتجاه وهمية فوق هذه الواجهات.

ينتمي تدفق HTTP العام إلى `@go-like/web` وإلى Handler الأصلي لإطار العمل. أما `@go-like/client` و`@go-like/transport` الداخليان فيقدمان حالياً استدعاءات `Message` أحادية فقط، ولا ينشران Fetch Transport أو Stream Client منفصلين.

هذا الفصل مهم لأن أجسام Web تُقرأ مرة واحدة. ينبغي للـ middleware ألا يقرأ الجسم إلا إذا كان سيوفر بديلاً عنه، ويجب أن ينتقل الإلغاء عبر إشارة الطلب وعبر `Context` الموجود في أول المعاملات. تتحقق طبقة النقل أيضاً من أن مقاطع التدفق هي `Uint8Array`؛ فإذا وصل مقطع غير صالح أصبح ذلك خطأ بروتوكول واضحاً، لا بيانات فارغة بصمت.

مرّر معالج Fetch الأصلي لإطارك إلى `@go-like/web` لنقاط HTTP العامة. تستطيع Hono وElysia وH3 إنشاء SSE أو استجابات متدفقة أو ترقيات WebSocket خاصة ببيئة التشغيل مباشرة. يحافظ go-like فقط على هوية `Request` و`Response` والتدفق والخطأ الأصلية، ولا يحاول إعادة تعريفها.

ينظّف `contextHandler` سياق Context الخاص به عند اكتمال Handler وإرجاع Response، وليس عند نهاية تدفق body. يجب أن يتابع المنتج طويل العمر `request.signal` أو سياق إلغاء يملكه صراحةً.

يوفّر `@go-like/protoc-gen-like` شيفرة Protobuf RPC مولّدة تضع `Context` أولاً، باستخدام Protobuf-ES. يوفّر `@go-like/transport-grpc-buf` عبر Fetch استدعاءات Connect/gRPC-Web الأحادية وتدفق استجابات الخادم؛ ويضيف `/native` معيار gRPC بالأنماط الأربعة، بما فيها تدفق طلبات العميل والتدفق ثنائي الاتجاه. هذا مسار مستقل عن Transport SPI الأحادي.

لا تعني اختبارات التوافق ضماناً للإنتاج: سُجّلت مشكلة تصريف تدفق بطيء في Deno 2.9.5/2.9.7، وبقاء مؤقّت deadline في Connect 2.1.2 بعد إلغاء تدفق استجابة متوقف مؤقتاً، وعدم وصول إلغاء Fetch في Bun 1.4.2 إلى خادم صامت بعد أول جزء. راجع [الأدلة والقيود](/reference/claims#stream-cancellation-limits)؛ لم تُصلح هذه المشكلات في go-like.
