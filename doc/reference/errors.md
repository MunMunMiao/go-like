# Error handling

go-like uses identity for Context termination, a branded guard for service failures, structural codes for framework and provider failures, and native `AggregateError` for multiple failures. Keep those layers distinct; a message is diagnostic text, not a contract.

## Match failures in this order

```ts
if (error === canceled || error === deadlineExceeded) {
  // Context termination
} else if (isServiceError(error)) {
  // Application service failure
} else if (error instanceof AggregateError) {
  // Inspect error.errors in order
} else if (typeof error === "object" && error !== null && "code" in error) {
  // Match one documented GO_LIKE_* code
} else {
  // Classify by documented origin, or propagate unchanged
}
```

Import `canceled` and `deadlineExceeded` from `@go-like/context` and `isServiceError` from `@go-like/transport`. When working from a `Context`, compare `ctx.err()` with the sentinels and use `cause(ctx)` for an application-supplied cancellation cause.

Do not branch on `error.message`. Messages are allowed to change and may contain provider text. Do not use `instanceof` for structural provider errors: different realms, package copies, and frozen object construction make class identity the wrong contract. Match a documented `code` and validate any fields your policy consumes.

`ServiceError.code` is application-owned and is not part of the `GO_LIKE_*` catalog. Recognize it only with `isServiceError(error)` before interpreting its `code`, `status`, or `metadata`.

`TypeError` and `RangeError` are common programmer-error examples, not the complete class. Classify application and invariant failures from their documented origin or boundary. Propagate an unclassified failure unchanged, without automatic retry, conversion, or message matching. Treat an `Error` as native or upstream only when it is known to come from a documented native or provider boundary; preserve its identity for local, redacted diagnostics and let that provider or runtime's policy decide whether retry is permitted.

## Retry and reconcile

Retry is replay authorization, not an error-name reaction.

| Failure class                                                                                | Default policy                                                                   | Required caller decision                                                                                                |
| -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| State, closed, already-started, unsupported, validation, authentication, or protocol failure | Do not retry automatically                                                       | Fix lifecycle order, input, capability, credentials, or provider data                                                   |
| Transport, HTTP, or provider availability failure                                            | Retry only when the operation is replayable and an explicit policy authorizes it | Bound attempts and backoff; preserve the original failure for diagnostics                                               |
| Uncertain mutation, lease loss, or post-commit cleanup failure                               | Reconcile first; never blindly replay                                            | Read authoritative state, determine whether the mutation committed, then repair or issue a new guarded mutation         |
| Conflict, compacted cursor, expired snapshot, or no endpoint                                 | Do not repeat the same request unchanged                                         | Refresh the revision, cursor, snapshot, or discovery state and re-evaluate business intent                              |
| Shutdown timeout or unexpected terminal state                                                | Do not restart the same one-shot owner                                           | Observe the real native terminal, reconcile owned resources, then create a new owner only if application policy permits |

An HTTP status alone does not prove replay safety. A read may be replayable; a write may require an idempotency key, compare-and-set token, or authoritative readback. `GO_LIKE_ETCD_STORE_CLEANUP` explicitly means the mutation committed, so replaying it can duplicate work.

## Traverse every aggregate failure

`AggregateError` means more than one failure was retained. Inspect every entry in `error.errors` in order, recurse into nested aggregates, and record each failure without replacing it with the aggregate message.

Do not assume that `errors[0]` or `cause` is primary unless the package explicitly declares that ordering. Examples of declared order are narrow: the Client completed-call path retains response/cleanup semantics documented by the Client, Node Web places the primary lifecycle failure before cleanup failures, and the NATS adapters retain their observed native failure order. Those rules do not define a repository-wide aggregate ABI.

## Cause and redaction boundaries

`Error.cause` is local diagnostic state. Existing `Error` rejections retain their identity. At the explicitly normalized File Store and HTTP application/native boundaries, a non-`Error` rejection receives a fixed wrapper message and the original value as standard, non-enumerable `Error.cause`.

That cause is not written to service wire envelopes or framework-owned completion logs, metrics, or trace fields. Pino, Winston, and OTel adapters omit raw Error, message, stack, cause, body, headers, metadata, URL/path, and payload data. Secret-bearing Config, Registry, Consul Store, etcd Store, and Vault boundaries may replace or omit foreign rejection graphs; do not infer that every provider preserves an upstream cause.

An application-supplied `TransportLogger` may receive a local wrapper `Error` in diagnostic fields. The application owns that logger and is responsible for redacting any recursively serialized message, stack, cause, Request, headers, credentials, or payload data.
